# Phase 1 – ACME Project Tracking, Increment 1

Status as of 2026-11-24, branch `feature/increment-1` (not pushed).

**In short:** sign-in and project management (list, filter, create, edit,
delete) with role-based permissions are built, tested, and deployed to AWS at
<https://detyiwrgyf771.cloudfront.net>. Backend and frontend can be redeployed freely; never run
`bin/cleanup-environment.sh`.

---

## 1. What was built

### Backend (Python 3.13 Lambdas, PostgreSQL)

| Piece | Where | What it does |
| --- | --- | --- |
| Schema | `backend/_db/migrations/001_users_and_projects.sql` | `users` (email unique and lowercase, role enum, bcrypt hash, active flag) and `projects` (unique code, status enum, dates with start ≤ end, owner FK) |
| Derived data | `backend/_db/migrations/002_project_details_view.sql` | `project_details` view adds the owner's name; derived values come from queries, not stored columns |
| Admin seed | `backend/_db/seed_admin.sql` | Creates the first admin from `ADMIN_EMAIL` / `ADMIN_PASSWORD`; never overwrites an existing user |
| Shared library | `backend/_common/` | Routing and consistent JSON errors (`http.py`), DB access with parameterized SQL only (`db.py`), JWT (`auth.py`), bcrypt (`passwords.py`), role rules (`permissions.py`), input validation (`validation.py`) |
| Auth service | `backend/auth/` → `/api/auth` | `POST /login` (bcrypt check, 30-minute HS256 JWT with `sub` and `role`), `GET /me` |
| Projects service | `backend/projects/` → `/api/projects` | List with `?status=` and `?q=` (name/code search), get, create, update, delete; 409 on duplicate code |
| Migrations Lambda | `backend/_migrate/` | Runs the same migrations and admin seed inside the AWS VPC (see section 3) |

**Roles**

| Role | Projects |
| --- | --- |
| admin | Create, edit and delete any project |
| project_manager | Create; edit and delete only projects they own |
| team_lead | Read only (for now) |
| viewer | Read only |

Every request is checked by the backend: 401 without a valid token, 403 when
the role does not allow the action. All errors share one shape:
`{"error": {"code", "message", "details"}}`.

### Frontend (React 19, MUI, react-responsive, react-router)

| Piece | Where |
| --- | --- |
| API layer (token in `sessionStorage`, 401 handling) | `frontend/src/services/` |
| Session, route guard, role rules (mirror of the backend, only to hide buttons) | `frontend/src/auth/` |
| Login page, projects list, create/edit form | `frontend/src/pages/` |
| Table on desktop, cards on mobile, filters, status chip, delete confirmation | `frontend/src/components/` |

### Scripts

| Script | Purpose |
| --- | --- |
| `bin/migrate.sh` | Local migrations and admin seed with `psql`, tracked in `schema_migrations` |
| `bin/sync-common.sh` | Copies `backend/_common` into each service as `common/` (gitignored copies) |
| `bin/migrate-cloud.sh` | Invokes the migrations Lambda; hashes the admin password locally and sends only the hash |
| `bin/start-dev.sh` (changed) | Runs migrations and the sync step; installs pip packages for the Lambda runtime (3.13, x86_64) and fails loudly |
| `bin/deploy-backend.sh` (changed) | Runs the sync step, and `migrate-cloud.sh` after `terraform apply` |
| `bin/proxy-server.js` (changed) | Forwards the `Authorization` header; 404 for unknown endpoints |

### Infrastructure changes (`infra/`)

| Change | File | Why |
| --- | --- | --- |
| `random_password.jwt_secret` passed to the Lambdas as `JWT_SECRET` | `main.tf`, `locals.tf` | Token signing secret, generated by Terraform |
| Private `migrate` Lambda (no Function URL, no CloudFront route) | `migrate.tf` | Aurora is only reachable inside the VPC |
| API cache policy with `Authorization` in the cache key, TTL 0 | `cloudfront.tf` | CloudFront does not forward `Authorization` otherwise, so signed-in requests would get 401 |
| `auth` Lambda gets 1024 MB (others stay at 128 MB) | `lambda.tf` | Lambda CPU scales with memory; bcrypt took ~4.6 s per login at 128 MB |
| Connection timeout 10 s → 30 s | `backend/_common/db.py` | Aurora takes ~15 s to resume after pausing |

The provided VPC, security group, Lambda IAM role, state bucket and tags are
unchanged.

## 3. How it runs

### Locally

```sh
export ADMIN_EMAIL=admin@acme.test
read -rsp "Admin password: " ADMIN_PASSWORD && echo && export ADMIN_PASSWORD
./bin/start-dev.sh            # http://localhost:3000
```

### In AWS

```sh
export ADMIN_EMAIL=you@acme.example
read -rsp "Admin password: " ADMIN_PASSWORD && echo && export ADMIN_PASSWORD
./bin/deploy-backend.sh
./bin/deploy-frontend.sh
```

- Account `177348319870` (shared workshop account), region `ap-south-1`.
  Credentials come from `bin/setup-participant.sh` and expire after a few hours;
  the deploy scripts refresh them.
- The organizers pre-created the Aurora cluster (`coding-workshop-rds-57b7f111`),
  CloudFront distribution (`E15PHDY9O3MQSY`) and website bucket. The deploy
  added the Lambdas, the API routes and the cache policy.
- Migrations run in the private `migrate` Lambda after each backend deploy.
  The admin password is hashed locally; only the hash is sent, so it is not in
  Terraform state, Lambda settings or logs.
- The site and API are public on the internet; data is protected by sign-in.
  The `auth`/`projects` Function URLs are also directly reachable (repo
  default, `authorization_type = "NONE"`).

## 5. Where we are now, and decisions

**Decisions (2026-11-24):**

1. **Lambda log groups were changed outside Terraform** (KMS encryption and
   3653-day retention, presumably the organizers' automation). A backend
   deploy resets them to no encryption and 7 days. Accepted: the environment
   is wiped after 48 hours, so retention does not matter. `deploy-backend.sh`
   can be run freely. Only risk: if the role may not remove the KMS key, the
   deploy stops with `AccessDenied` on the log groups; then make Terraform
   match their settings instead.
2. **Infra edits**: settled. The admin is pre-seeded by the private migrations
   Lambda (the standard pattern); all other data is created through the UI or
   API.
3. **Terraform state upgraded to 1.17.2** (was 1.15.7): ignored unless it
   breaks something.
4. **Never run `bin/cleanup-environment.sh`.** `terraform destroy` would
   delete the organizer-created Aurora cluster and CloudFront distribution; a
   redeploy would get a new URL, an empty database, and might not be allowed
   to recreate them at all.

**Known limits (by design for Increment 1):**

- The first request after Aurora has been idle is slower while it resumes
  (`min_capacity = 0`). This is the organizers' setting and is **not to be
  changed without asking twice**: keeping Aurora running costs ~$1.40/day.
- Access tokens only (30 minutes), no refresh token; token in `sessionStorage`.
- No login rate limiting or lockout.
- No user management UI; other users are created with SQL (see
  `docs/acme-project-tracking.md`).
- Two migration runners (`migrate.sh` locally, the Lambda in AWS), sharing the
  same files and bookkeeping.

**Not started:** anything beyond Increment 1.

More detail on setup and trade-offs: `docs/acme-project-tracking.md`.
